# Bot wake API (DENE-1792; integration contract for DENE-1793)

Based on PR #626's `personal_access_token.kind=bot`; the Bot ID survives key
rotation. No new identity or extra content grants. Existing API clients remain
compatible with the expanded schema. Migration 660, generated by `make sqlc`.

## Routes and access

All routes require authenticated workspace membership.

- GET/PUT `/api/workspaces/{id}/bots/{botId}/wake`: the matching Bot PAT or a
  human workspace owner/admin. A Bot PAT cannot administer another Bot, even
  when both belong to the same administrator. Task/cloud/managed machine
  credentials cannot act as human administrators here.
- GET the same path plus `/events` or `/pending`: same gate; additionally filter
  each receipt by **both** the querying member's and PAT owner's current source
  visibility. No private chat override for admins. Public Chat projection and the
  creator's private-agent read gate are also preserved. Missing/deleted sources fail
  closed. Recheck permissions before sending too.
- GET `/api/workspaces/{id}/bots/mentions`: member-visible identity directory,
  `[{id,name,type:"bot",bot_type:"grok"}]`; no token metadata. Optional `issue_id`
  or `chat_session_id` (one only) filters to Bots that can read that source and
  first verifies the caller can read it. Inactive Bots are omitted. Use this
  endpoint for completion, not the admin-only existing `/bots` endpoint.

GET/PUT response has exactly:

```json
{"webhook_configured":false,"events":["mention","started","done","blocked","needs_kun","task","chat"],"hourly_limit":6,"quiet_hours":{"enabled":true,"start":"23:00","end":"08:00","timezone":"Asia/Shanghai"}}
```

PUT patches supplied fields. Do not send `webhook_configured`. `webhook_url` and
`webhook_key` must be supplied together, never echoed. Two empty strings remove
credentials. Key is the exact Authorization header value (including scheme).
Supported event names are unique; limit 0..120; times HH:MM and a valid IANA
zone. Equal start/end means all day. `events:[]` disables events; limit 0 pauses.
No extra top-level enabled field. Settings changes do not replay pending events.

Events/pending query: `limit=1..100` (default 50), `before=<sequence>`.
Response `{"events":[...],"next_cursor":"..."}`; empty cursor means end.
A filtered page can be empty with a continuation cursor; continue paging. Each
row has `event_id`, `sequence`, `type`, `issue_id`, `chat_session_id`, `status`,
`reason`, `attempts`, `created_at`, nullable `sent_at`/`received_at`. Absent source
IDs are empty strings. Reasons are fixed text/status codes, never endpoint,
response body, key or transport errors. No webhook secrets in response models.

## Delivery semantics

Source-transaction triggers insert the persistent outbox, so rollback means no
notification. Repeated mention in the same message/comment is unique per Bot
and source, including edits; a different message is a different event. All
recipients of a source event share its generated event ID. The worker polls the
local durable outbox each second (not Grok or a Mac bridge), uses SKIP LOCKED,
serializes the rate decision on the Bot row and counts **all attempts**, including
retries, in a shared rolling one-hour window. Settings updates serialize on the
same row. A request already in flight may complete after a rule changes.

- mention: explicit Markdown `mention://bot/<UUID>` in comment/chat or new
  issue description; only named Bots receive it. A mention adds a persistent
  Bot watch for that issue/chat. Edits may add a previously unmentioned Bot.
- started/done/blocked: issue status transitions to in_progress/done/blocked.
- needs_kun: new issue_summon, the existing human decision mechanism.
- task: new issue or changed member assignee. Watches plus existing PAT-owner
  member assignments/subscriptions determine lifecycle recipients.
- chat: subsequent messages in a watched chat. No token-owner-wide chat fanout.

States: queued -> sending -> received/failed/uncertain, or pending without send.
HTTP 200 means receipt only. Pre-send failures/429/503 have at most 3 attempts,
5s then 10s backoff. Other 5xx, timeout after headers or interrupted sending are
uncertain, never replayed automatically. Stale sending is reconciled after two
minutes. Disable/quiet/limit/inactive/access/config failures become pending.
Pending is an append-only inspection surface in this version; reading does not
acknowledge or remove a row. Receivers deduplicate by event_id.

POST payload: event_id, type, issue_id/chat_session_id, author {type,id}, time,
summary (event type + current title, at most 180 runes), authenticated API url,
attachments [{url,size_bytes,sha256}]. No comment/chat body. Headers:
Content-Type application/json, Authorization (exact configured value),
X-Multica-Event-ID. URLs point to authenticated API paths, never signed storage
capabilities. Legacy attachments without a recorded digest are omitted from the
push and can be fetched via the normal authorized metadata route.

## Secrets and network

AES-256-GCM via existing secretbox. Optional base64 32-byte
MULTICA_BOT_WAKE_SECRET_KEY; otherwise domain-separated HMAC-SHA256 derivation
from JWT_SECRET. Invalid explicitly configured key fails closed. Keep key stable
across replicas/restarts. Public HTTPS only, DNS checked again at connection,
no proxies/redirects. URL query values are encrypted too. Existing operator-only
MULTICA_PLUGIN_DEV_ORIGINS exact-origin exception enables local HTTP acceptance;
never populate it with production/internal endpoints casually. Worker logs no
secrets. Local tests do not prove Grok accepts a particular authorization scheme.

## Attachments and CLI

New uploads compute and store sha256 server-side before object write. Optional
multipart sha256 mismatch returns 400; chunk metadata carries it through to the
same final validation. CLI upload always supplies it. External Bots can use
`multica attachment upload <path> --issue <id>` without a chat-task token;
this attaches to the authorized issue without posting a comment. Single metadata GET lazily
hashes legacy server-owned storage after access checks, validates stored size,
and saves only if absent. If storage is unavailable, metadata/preview access
remains compatible; the verified CLI refuses missing digests. This cannot attest
historic integrity before first hash.
Source-context clones retain an existing digest. CLI download checks sha256 and
size before creating a file, then writes a temporary file and renames; rejected
bytes are discarded and temporary files removed. A preexisting good file is
never deleted for a corrupt response. Old servers without digest are refused.

`multica bot wake get/set/events/pending <bot-id>`; set accepts exactly one of
`--config-file` and `--config-stdin`. Output JSON has no URL/key. Full UUID
required, so a Bot does not need the admin directory to resolve itself.

## Acceptance boundary

Local tests exercise real PostgreSQL transactions and HTTP socket delivery to a
local receiver, encryption, visibility, limits, quiet, dedupe, finite retries,
uncertainty and file digest failures. They are not real Grok acceptance. Parent
integration still owns actual routine credentials/header scheme, sub-minute
Grok execution/reply, paused-machine wake, charges, UI and long-term instructions.
