# Bot wake API (DENE-1792; integration contract for DENE-1793)

Based on PR #626's `personal_access_token.kind=bot`; the Bot ID survives key
rotation. No new identity or extra content grants. Existing API clients remain
compatible with the expanded schema. Migrations 660–664, generated by `make sqlc`.

Trusted provenance from DENE-1794 (migration 662) is integrated by migration
663. Deploy #626 and migrations 660–664 with the matching application before
enabling delivery; do not send Bot writes to older replicas. This contract
covers local verification, not actual Grok execution or production deployment.

## Routes and access

All routes require authenticated workspace membership.

- GET/PUT `/api/workspaces/{id}/bots/{botId}/wake`: the matching Bot PAT or a
  human workspace owner/admin. A Bot PAT cannot administer another Bot, even
  when both belong to the same administrator. Task/cloud/managed machine
  credentials cannot act as human administrators here.
- GET the same path plus `/events` or `/pending`: same gate; additionally filter
  each receipt by **both** the querying member's and PAT owner's current source
  visibility. No private chat override for admins. Public Chat projection and the
  creator's private-agent read gate are also preserved. Missing/deleted sources fail
  closed. Recheck permissions before sending too.
- GET `/api/workspaces/{id}/bots/mentions`: member-visible identity directory,
  `[{id,name,type:"bot",bot_type:"grok"}]`; no token metadata. Optional `issue_id`
  or `chat_session_id` (one only) filters to Bots that can read that source and
  first verifies the caller can read it. Inactive Bots are omitted. Use this
  endpoint for completion, not the admin-only existing `/bots` endpoint.

GET/PUT response fields (additive):

```json
{"inherit_owner_follows":false,"webhook_configured":false,"events":["mention","started","done","blocked","needs_kun","task","chat"],"hourly_limit":6,"limited_count":0,"wake_from":{"member":{"mode":"all","ids":[]},"agent":{"mode":"all","ids":[]},"bot":{"mode":"none","ids":[]}},"quiet_hours":{"enabled":true,"start":"23:00","end":"08:00","timezone":"Asia/Shanghai"}}
```

`inherit_owner_follows` is a boolean, default false, readable/writable by the
same Bot/admin gate as other settings. When enabled, issue lifecycle/task/summon
events also consider the PAT owner's current member subscriptions and member
assignments. It does not copy these into explicit Bot watches, inherit every chat
the owner can read, or fan out mentions addressed only to other Bots. Disabling
stops new inherited events; queued inherited events become pending with
`owner inheritance disabled`. Unfollowing/unassignment before send yields
`owner no longer follows source`. Current source visibility, sender rules, quiet
hours, event types, the ordinary-event rate limit and root budget still apply.
Inheritance changes do not replay pending events held by inheritance policy. Explicit Bot watches/mentions remain valid
independently of this switch. Frontend should bind its switch directly to this
field; no client-side subscription expansion.

PUT patches supplied fields. Do not send `webhook_configured`. `webhook_url` and
`webhook_key` must be supplied together, never echoed. Two empty strings remove
credentials. Key is the exact Authorization header value (including scheme).
Supported event names are unique; limit 0..120; times HH:MM and a valid IANA
zone. Equal start/end means all day. `events:[]` disables events; limit 0 pauses.
No extra top-level enabled field. Saving settings makes quota/quiet deferred events eligible for immediate rechecking; other policy blocks and uncertain deliveries are not replayed.

Events/pending query: `limit=1..100` (default 50), `before=<sequence>`.
Response `{"events":[...],"next_cursor":"..."}`; empty cursor means end.
A filtered page can be empty with a continuation cursor; continue paging. Each
row has `event_id`, `sequence`, `type`, `issue_id`, `chat_session_id`, `status`,
`reason`, `attempts`, `created_at`, nullable `sent_at`/`received_at`. Absent source
IDs are empty strings. Reasons are fixed text/status codes, never endpoint,
response body, key or transport errors. No webhook secrets in response models.

## Delivery semantics

Source-transaction triggers insert the persistent outbox, so rollback means no
notification. Repeated mention in the same message/comment is unique per Bot
and source, including edits; a different message is a different event. All
recipients of a source event share its generated event ID. The worker polls the
local durable outbox each second (not Grok or a Mac bridge), uses SKIP LOCKED,
serializes the rate decision on the Bot row and counts non-mention attempts, including
retries, in a rolling one-hour window. Settings updates serialize on the
same row. Mention events are selected before other ready events, sharing the
ordinary-event limit (default 6) is bypassed by mentions, which consume no hourly
quota; zero explicitly pauses all pushes, and quiet hours still apply to mentions.
Legacy attempts recorded before this release age out of the window after one hour.
A request already in flight may complete after a rule changes.

`wake_from` contains member/agent/bot rules `{mode: "all"|"none"|"list",ids:[]}`;
list IDs must be UUIDs (up to 100). Bot defaults none, member/agent default all.
The entire map is replaced when supplied. Sender rejection and self-Bot events
are held pending with fixed reasons. The outbox snapshots the authenticated current writer and Bot provenance
inside the source transaction; it never substitutes the issue creator. Some
issue writes lack transaction-local actor settings, leaving system/null attribution.
The worker recovers the agent from a workspace-scoped source run when possible;
otherwise delivery proceeds with author type/id empty and note="source attribution unavailable".
Known actors still obey sender filters and self-wake suppression; visibility,
inheritance, event, quiet and chain checks always apply.

- mention: explicit Markdown `mention://bot/<UUID>` in comment/chat or new
  issue description; only named Bots receive it. Fenced/indented code, inline
  backtick spans and blockquote lines are excluded. SQL and Go use the same
  conservative line grammar with a parity test. Unclosed backticks suppress the
  rest of that line; this is a notification grammar, not full Markdown rendering. A mention adds a persistent
  Bot watch for that issue/chat. Edits may add a previously unmentioned Bot.
- started/done/blocked: issue status transitions to in_progress/done/blocked.
- needs_kun: new issue_summon, the existing human decision mechanism.
- task: new issue or changed assignee on an explicitly watched source. Owner
  assignments/subscriptions fan out only with `inherit_owner_follows:true`. Explicit bot
  assignment is captured when supported by the issue assignment API; this
  migration does not add Bot assignment support to that API.
- chat: subsequent messages in a watched chat. No token-owner-wide chat fanout.

States: queued -> sending -> received/failed/uncertain, or pending without send.
HTTP 200 means receipt only. Pre-send failures/429/503 have at most 3 attempts,
5s then 10s backoff. Other 5xx, timeout after headers or interrupted sending are
uncertain, never replayed automatically. Stale sending is reconciled after two
minutes. Disable/quiet/limit/inactive/access/config failures become pending.
Quota/quiet pending events are automatically reconsidered each second,
in sequence order within ordinary ready events, including events held before
this release. Acknowledged or execution-confirmed events are excluded.
GET/PUT return the actually saved hourly_limit and limited_count, counting only
held events visible to both the querying member and the Bot owner.
Reading never acknowledges. `/pending` returns only unacknowledged pending,
failed and uncertain events. This is a stable unacknowledged scan, not a creation
sequence delta: page using `before`/`next_cursor`, including empty filtered pages;
after the end, restart without `before`. Process then POST `/pending/ack` with
`{"event_ids":[...]}` (1..100). The batch checks every event and visibility and
commits all or none. Duplicate acknowledgements succeed without changing time.
Persisting a last-created sequence as a high-water mark is NOT supported. Old
queued events that fail after a scan and transactions that commit out of sequence
appear in the next scan. On restart begin again at the first page. A crash before
ack causes replay to the reader; deduplicate by event_id. The global bigserial is
neither Bot-contiguous nor commit-ordered. Only unsent events held by quota/quiet policies are automatically released;
failed/uncertain sends retain their existing retry and review semantics.

POST `/events/{eventId}/woken` with `{}` and `/events/{eventId}/result` with
`{"result_url":"<canonical source API URL>"}` records server receive timestamps.
Both use the existing recipient/admin and dual source visibility gate. Another
Bot cannot acknowledge this Bot's event. `woken_at`, `result_at`, `result_url`,
`acknowledged_at` are additive event fields. Duplicate execution receipts preserve
timestamps; out-of-order result then woken preserves both. HTTP status/received_at
remain separate. A result does not fabricate woken_at. This version only accepts
the event's exact issue/chat API URL, not arbitrary comment or external URLs.
For pending/failed/uncertain events a review acknowledgement neither confirms
execution nor retries delivery. The same /pending/ack endpoint (and CLI wake ack)
records woken_at for received/sending events, including a receipt sent while the
webhook request is in flight. Batch validation remains atomic and idempotent.
The legacy bare /events/{eventId} and /events/{eventId}/ack paths accept execution
receipts as aliases for /woken.

POST payload: event_id, sequence, source_id, parent_id, source_task_id, root_id,
hop, web_url, ack_url (the CLI /pending/ack endpoint), ack_body ({event_ids:[event_id]}),
woken_url, result_url (POST endpoints; send {} or {result_url:payload.url}), type, issue_id/chat_session_id,
author {type,id,name?,via_bot_id?,via_bot_name?}, time,
summary (event type + current title, at most 180 runes), authenticated API url,
attachments [{url,size_bytes,sha256}]. No comment/chat body. Headers:
Content-Type application/json, Authorization (exact configured value),
X-Multica-Event-ID. URLs point to authenticated API paths, never signed storage
capabilities. `parent_id` identifies the containing issue/chat; `source_id`
identifies the triggering comment/message (or issue/summon for lifecycle events).
For a threaded comment reply, use the source comment ID, not the container ID. Legacy attachments without a recorded digest are omitted from the
push and can be fetched via the normal authorized metadata route.

## Secrets and network

AES-256-GCM via existing secretbox. Optional base64 32-byte
MULTICA_BOT_WAKE_SECRET_KEY is required by the production deployment procedure;
legacy installations retain domain-separated HMAC-SHA256 derivation
from JWT_SECRET. Invalid explicitly configured key fails closed. Keep key stable
across replicas/restarts. Before enabling the worker in production, configure the
same independent key on every replica using the deployment secret store. Do not
simply replace a legacy JWT-derived key: existing ciphertext will not decrypt.
Pause delivery, retain the old key securely, rewrite each Bot's URL/key via the
normal PUT using receiver-owned credentials under the new key, verify on every
replica, then resume. No plaintext export endpoint exists. On decryption failure
the event stays pending (`webhook decryption failed`), never leaks ciphertext or
key and is not replayed automatically. Roll back the key only if no credentials
have been rewritten; otherwise reconfigure all affected Bots. Public HTTPS only, DNS checked again at connection,
no proxies/redirects. URL query values are encrypted too. Existing operator-only
MULTICA_PLUGIN_DEV_ORIGINS exact-origin exception enables local HTTP acceptance;
never populate it with production/internal endpoints casually. Worker logs no
secrets. Local tests do not prove Grok accepts a particular authorization scheme.

## Attachments and CLI

New uploads compute and store sha256 server-side before object write. Optional
multipart sha256 mismatch returns 400; chunk metadata carries it through to the
same final validation. CLI upload always supplies it. External Bots can use
`multica attachment upload <path> --issue <id>` without a chat-task token;
this attaches to the authorized issue without posting a comment. Single metadata GET lazily
hashes legacy server-owned storage after access checks, validates stored size,
and saves only if absent. If storage is unavailable, metadata/preview access
remains compatible; the verified CLI refuses missing digests. This cannot attest
historic integrity before first hash.
Source-context clones retain an existing digest. CLI download checks sha256 and
size before creating a file, then writes a temporary file and renames; rejected
bytes are discarded and temporary files removed. A preexisting good file is
never deleted for a corrupt response. Old servers without digest are refused.

`multica bot mentions [--issue <uuid>|--chat <uuid>]` provides the scoped directory.
`multica bot wake woken <bot-id> <event-id>`, `result <bot-id> <event-id>
--result-url <source API URL>` and `ack <bot-id> <event-id>...` use the routes above.
`multica bot wake get/set/events/pending <bot-id>`; set accepts exactly one of
`--config-file` and `--config-stdin`. Output JSON has no URL/key. Full UUID
required, so a Bot does not need the admin directory to resolve itself.

## Acceptance boundary

Local tests exercise real PostgreSQL transactions and HTTP socket delivery to a
local receiver, encryption, visibility, limits, quiet, dedupe, finite retries,
uncertainty and file digest failures. They are not real Grok acceptance. Parent
integration still owns actual routine credentials/header scheme, sub-minute
Grok execution/reply, paused-machine wake, charges, UI and long-term instructions.

## Causality, lifecycle and verification limits

Comment/chat source triggers snapshot their trusted Bot provenance and source
run; issue mutations consume the statement-local actor settings from 662.
Summon records carry the same authenticated source and task. Direct Bot writers
use author.type=bot; agent replies retain author.type=agent and include their Bot
provenance. Private agent identity and nonmember author identity are redacted.
Deleted Bot credentials remain as audit tombstones; the directory omits them,
the worker marks old queued events pending, and settings PUT returns 410.

`bot_wake_cause` stores each Bot's current root, so omitting a parent/hop header
cannot create a new chain. `bot_wake_chain` serializes a maximum of four automatic
wake admissions across a root, including all branches. This is deliberately more
conservative than four hops per branch. Dispatch records the cause before network
I/O; retries of the same event reuse its admission and still count toward the
hourly attempt budget. A new genuine member event starts a new root. Independent
Bot actions remain in their last server-owned root until another delivered event
provides a cause; a Bot cannot reset this with client-supplied metadata.

Task queue inserts inherit from a parent run, triggering comment, or authenticated
Bot association and consume the same root budget. Runs persist wake_root_id and
wake_hop; task-token replies recover them through source_task_id. At the cap the
run is persisted cancelled with error `bot wake chain limit (4)` and cannot be
requeued. Bot delivery at the cap stays pending with that reason. Genuine direct
human runs are not charged to an old automation root. Existing pre-upgrade queued
events without trusted lineage stay pending (`source lineage unavailable`).
No arbitrary client `hop`, actor header or payload can change these counters.

Local acceptance includes an authenticated HTTP Bot A -> Bot B -> agent task ->
Bot A chain, a worker recreation, cap/cancellation, source actor differing from
issue creator, repeated/reordered receipts, old failed events, out-of-order
commits and permission-filtered empty pages. CLI subprocesses can be exercised
against the local HTTP fixture with BOT_WAKE_TEST_CLI pointing at the built CLI.
This is not a real cloud agent runtime or a real Grok receiver. Actual paused
cloud-machine wake, reply latency, costs and production replica rollout remain
parent acceptance. Explicit Bot watches are created by mentions; owner issue
inheritance is opt-in with `inherit_owner_follows` (migration 664). `task` alone
does not claim that a cloud execution was launched.

## DENE-1799 review regression coverage

Both IssueService creation branches (`CreateIssue` and `CreateIssueWithOrigin`)
pass the authenticated context's task ID into the statement-local source setting.
Task tokens retain agent authorship, via-Bot snapshot and the run's persisted
root/hop even after that Bot's current cause changes. Request-supplied origin,
actor or hop values are not used to establish this source. Local regression
coverage includes the agent=none/Bot=all counterexample on both branches.

## Self-host deployment injection (DENE-1800 prerequisite)

`docker-compose.selfhost.yml` explicitly forwards `MULTICA_BOT_WAKE_SECRET_KEY`
only to the backend. The local-build override retains that environment;
`backend-green` extends the same backend definition, so both colours receive the
same operator-supplied key. `scripts/install.sh`, `scripts/selfhost-wait.sh` and
`scripts/selfhost-autoupdate.sh` use these Compose files. Mirror the protected
injection in the unattended updater's environment as well as an interactive shell.
Do not rely on a one-off shell export surviving service restarts.

Provision a base64-encoded 32-byte random key once in the deployment secret store
or an operator-owned mode-0600 env file outside Git. Compose accepts that file via
`--env-file <protected-file>` or `COMPOSE_ENV_FILES`; the existing deployment `.env`
may hold it only if access is restricted and the file is excluded from backups
that are public and from repository commits. Shell environment overrides env-file
values: remove stale overrides before rollout. Never put the value in command
arguments, Git, tickets, logs, or `docker compose config` output. Preserve the
same protected input for backend/green, replicas and all later recreations.

This forwarding fix deliberately leaves missing values empty: existing
JWT-derived ciphertext continues to decrypt, and old deployments are not forced
to rotate. **Empty is not an acceptable production Bot-webhook enablement state.**
Before enabling new receiver credentials, operations must verify a nonempty,
valid independent key is configured on every backend, reporting only a boolean.
If any ciphertext already exists under the JWT-derived key, follow the pause and
receiver-owned credential rewrite procedure above before switching keys; this
patch does not automatically migrate or invalidate ciphertext. Invalid explicit
keys keep encryption unavailable rather than falling back to JWT_SECRET.

Local Compose rendering with synthetic keys checks published/build/blue-green
forwarding and repeat consistency without printing values. That check and the
existing independent secretbox-instance test do not prove a production restart:
DENE-1805 must verify persisted injection and matching running image on rollout;
DENE-1800 retains real Grok execution and cost acceptance.
