「redirect_url must be a valid URL」是什么问题

结论：是我们代码的问题，不是你的操作，也不是服务器地址配错。

创建 GitHub App 的流程

点「创建 GitHub App」→ 服务器生成一份「App 申请表」→ 浏览器把申请表交给 GitHub→ GitHub 检查申请表 ✗ 卡在这里→ 你输密码确认→ GitHub 按 redirect_url 跳回 ai.ferryway.cc→ 服务器保存 App，完成

申请表里有一项 redirect_url：GitHub 创建完 App 后要把你送回哪个地址。GitHub 认为这个地址不合法，直接拒收了整张表。

我实际查到的申请表内容

字段值判断
服务器地址https://ai.ferryway.cc✅ 正确
webhook 地址https://ai.ferryway.cc/api/webhooks/github✅ 正确
redirect_urlhttps://ai.ferryway.cc/api/github/app/callback?state=djF8MTcy…（一长串，共 269 个字符）❌ 问题在这

为什么这个地址不行

现在的做法

我们把一张「防伪凭证」（state，里面含工作区 ID、你的用户 ID、过期时间和签名）直接塞进了 redirect_url 的问号后面。
结果地址又长又带参数，GitHub 的校验不收。

GitHub 官方要求的做法

redirect_url 只写干净的地址 …/api/github/app/callback；
凭证放在「提交给 GitHub 的那个网址」上（github.com/settings/apps/new?state=…），GitHub 跳回来时会自动把 state 原样带回。
服务器接收那一端不用改。

影响范围

  • 自建实例上任何人都建不成 GitHub App（网页端、桌面端、CLI 的 setup-link 用的是同一份申请表）。
  • 这个功能是 DENE-981（设置页一键创建）、DENE-998（桌面端跳浏览器）刚加的，上线后大概率没真跑到 GitHub 这一步。
  • 智能体推代码、开 PR 不受影响；受影响的是服务器看 PR 状态这一侧。
修法（小改动）：服务端生成申请表时，把 state 从 redirect_url 挪到 GitHub 提交地址上。改完要真的点一次，让 GitHub 走完创建流程才算验收，只跑单测不够。
