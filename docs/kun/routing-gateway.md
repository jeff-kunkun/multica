# 自动选派的路由模型：端点与 Key 归工作区

## 这篇解决的问题

自动选派（DENE-633）里那个「路由模型」框填的是**裸模型 id**。它发往哪个端点、用谁的 Key，原来完全由部署级环境变量决定：

- `MULTICA_LLM_BASE_URL`
- `MULTICA_LLM_API_KEY`
- `MULTICA_LLM_DEFAULT_MODEL`（模型框留空时的兜底）

一个人自建、只有自己用的时候这没问题。**把实例交给团队之后就不成立了**：换个模型要 SSH 上服务器改环境变量再重启，而且改完是整台机器所有工作区一起换。"找运维"不是一个设置项。

现在端点和 Key 可以按工作区配，**两个字段都可选**：都留空就还是走部署那套，行为和改动前逐字一致。

## 三层优先级

| 工作区填了 | 实际发往 |
|---|---|
| 端点 + Key 都填 | 工作区自己的端点，用工作区自己的 Key |
| 只填一半 | **部署端点**（见下） |
| 都没填 | 部署端点 |

**只填一半为什么不报错、也不凑合用**：拿部署的 Key 去打一个运维没选过的主机，和拿工作区的 Key 去打部署的主机，都是把凭据送到不该去的地方。所以半填就整体回落到部署端点，并在设置里明写这件事——静默回落是"我自己的模型怎么一次都没被调用"这种一下午的由来。

## Key 存在哪

存在 `workspace.settings.routing.api_key_enc`，**AES-256-GCM 封好的密文**。

- 封装密钥是从 `JWT_SECRET` 用 HMAC 域分隔派生的（`multica/routing-gateway-key/v1`），所以**自建实例不需要多加环境变量**。想让这份凭据吃独立密钥，设 `MULTICA_ROUTING_SECRET_KEY`（base64 的 32 字节），它优先。
- 两个都没有 → 这个部署存不了工作区 Key，设置里的 Key 框直接置灰并写明原因；提交 Key 会收到 503 而不是被悄悄丢掉。
- **密文从不出服务端**。工作区读接口会把这个字段整个剥掉，客户端连打码版本都拿不到。

### 因此写入必须"继承"

客户端既然拿不到 Key，就没法把它原样传回来。所以设置写入这样处理 `routing` 块里的 `api_key` 字段：

| `api_key` | 行为 |
|---|---|
| 非空字符串 | 封装后替换 |
| 空字符串 `""` | **显式清除** |
| 字段不存在 | **沿用已存的** |

第三行是关键。任何一次与 Key 无关的设置保存（改模型、改阈值、改别的开关）都不带这个字段，如果"不存在"被理解成"清空"，第一次这样的保存就会把 Key 删掉，而路由会安静地停掉、界面上什么都看不出来。

界面上对应的是：端点 URL 跟着别的字段自动保存，**Key 只在按下「保存 Key」时才提交**——自动保存会把敲了一半的 Key 存进去。

## 模型怎么自动填

当路由开关已打开、模型框还是空的，而且当前端点已经确定后，设置页会向
`POST /api/workspaces/{id}/routing/models` 请求模型目录。这个请求只允许工作区
owner/admin 发起；服务端按上面的优先级解析端点，并在服务端内部使用已保存的 Key
请求 OpenAI-compatible 的 `/models`。返回给前端的只有去重排序后的模型 id，不会返回
Key、密文或厂商原始响应。

拿到目录后，模型框为空就自动填第一个模型，同时把全部 id 放进可选列表。已经手动
选过的模型不会被覆盖；端点不支持 `/models`、请求失败或返回空目录时仍可手动输入。

只填自定义 URL、还没有工作区 Key 时，不会拿部署端点的模型冒充自定义端点的模型；
等 URL 和 Key 成对保存后才读取自定义目录。两者都留空时，才会读取部署端点目录。

## 密钥轮换 / 数据库还原

密文用旧 `JWT_SECRET` 封的、服务器现在拿的是新的，或者把库还原到了另一个部署——`openRoutingKey` 一律返回空串，等价于"这个工作区没有 Key"：

- 路由回落到部署端点，不会拿垃圾去当凭据拨号；
- 设置里 `gateway_key_set` 报 false，界面显示"没有已保存的 Key"，提示重填。

**不做自动迁移**，重填一次就是全部代价。

## 自检那一栏在说什么

`GET /api/workspaces/{id}/routing/health` 多了三个字段：

- `gateway_scope`：`workspace` / `deployment`——同一个 host 名，归属不同，下一步动作也不同（在这一页改，还是去找运维）。
- `gateway_key_set`：**存了且能解开**。解不开的报 false。
- `workspace_key_storable`：这个部署能不能存工作区 Key。

`gateway_host` 只回 host，不回原始 URL：从厂商控制台粘出来的 URL 经常在 userinfo 里带着 token。

`gateway_configured` 的含义也跟着变了：现在是"**两边都没有端点**"，而不只是"部署没配"。原来的读法会在工作区刚刚自己填好端点的那一刻告诉他"这儿你改不了"。

## 不碰的

- 聊天自动起标题、后续建议等其它内部 LLM 用途仍然只走部署那套。工作区端点**只服务路由裁判**。
- 模型发现只服务路由设置页；它不把工作区 Key 交给浏览器，也不改变聊天或 Agent 运行时的模型目录。
- 路由的七条硬规则一条没动：不推进状态、只填空格、真人负责人的票整张不碰……换端点只换"问谁"，不换"怎么写"。
