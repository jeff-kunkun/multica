# ADR-0009: 备用运行时只能显式配置、同主人同提供商，不自动按系列挪

- status: accepted
- date: 2026-10-11

## 背景

一台 Mac 睡眠，绑在它上面的 52 个智能体全部停摆，Grok Bot 转来的验证码在队列里静默过期（DENE-1819）。父票最初的验收标准写的是：加急消息的绑定运行时离线时，「按智能体系列自动挪到同系列的在线运行时，或者直接失败」。

自动挪看起来省事，但运行时不是可互换的算力：它带着那台机器上的登录态、CLI、额度、本地目录和私密文件。工作区里其他在线运行时属于别的成员，或者装的是别的提供商（DENE-1843 的改绑候选表里，常在线的 ai-multica 只注册了 Grok）。「同系列」只是展示和派单偏好用的分类（见 CONTEXT.md「智能体系列」），说不了「这台机器能替那台干活」。

## 决策

1. **备用运行时是智能体上显式配置的一台**（`agent.fallback_runtime_id`）。没配就没有备用，加急消息直接拒绝并说明哪台离线、最后在线时间。
2. **服务端只接受同主人、同提供商、且调用者有权使用的运行时**；主运行时换成不匹配的，备用自动清空，不让一对错配的运行时静默存活。
3. **只有加急投递用它。** 普通聊天和任务单运行照旧只等主运行时；宽限（聊天 3 分钟、任务单 3 小时）和重试规则不因备用运行时而变。
4. **不按系列、不按「谁在线」自动挑。** 要让高时效智能体常在线，是改绑或补齐常在线机器的环境（`docs/kun/runtime-availability.md`），不是让平台替人猜。
5. **领取栅栏一处判。** 任务只能被它所写的那台运行时领取，加急任务写的是主运行时或备用运行时之一；备用不是「任何在线运行时都能抢」。「主运行时或显式备用都有资格」这条规则在 Go 侧只有一个出口 `service.AgentMayRunOnRuntime`，领取服务、领取响应构造、投递事务三处都调它，SQL 侧是领取、候选、提升、回收查询共用的同一谓词（`a.runtime_id = atq.runtime_id OR a.fallback_runtime_id = atq.runtime_id`）；真实改绑、撤销备用、跨主人或跨提供商、私有运行时各自的拦截照旧（DENE-1887）。

## 理由

- 运行时的主人边界是权限边界：把 Kun 的智能体挪到别人的机器上，等于把 Kun 的任务和聊天内容交给别人的登录态跑。
- 提供商边界是能力边界：Claude 席位挪到只有 Grok 的机器上，拿起了也跑不了，比明说「没人接」更糟。
- 显式配置的代价是每个高时效智能体要手工选一次备用；换来的是失败可解释——拒绝信息里只会出现人认识的两台机器。
- 「当场拒绝」优于「悄悄排队」：发消息的一方（通常是 Bot）能立刻改走别的路，这正是事故里缺的信号。

## 后果

- 父票验收标准里的「按系列自动挪」不实现；替代物是显式备用运行时加当场拒绝。
- 运维侧要维护改绑候选：哪些智能体该有备用、备用机器上要补齐什么环境，见 `docs/kun/runtime-availability.md`。
- 以后若要支持「同提供商的任意在线运行时」接手，改的是备用运行时的取值规则，不是把自动挑选加回加急投递。
- 唤醒任务（`issue wakeup`）、容量计算和过期回收不需要为备用运行时另写规则：唤醒任务只写主运行时，所以唤醒侧的「智能体还在这台运行时上」判断不碰备用；容量按任务所写运行时的机器算，备用机器用自己的额度；回收和候选查询已经带同一谓词。只有「任务写了备用运行时」这一种情况需要三处 Go 判断认备用，这就是 DENE-1887 修的地方。
