# ADR-0004: 跨工作区连通使用显式出口，不复用访客

- status: accepted
- date: 2026-10-03

## 背景

一个工作区（源方）想让另一个工作区（看方）的人只读看到自己若干项目的进展，又不想把这些人拉进来当成员。现成的「访客」档位看起来能凑合用：把对方的人一个个邀请成访客，再把项目共享给访客。但访客是**源方的成员**：每个人都要单独邀请，对方换人时还要跟着改。访客一旦成为成员，就能走源方所有既有接口（Issues、Projects、搜索、通知、WebSocket），每个接口都靠自己的过滤把访客挡在外面。只要有一个接口的过滤漏了，泄露的就是整条接口返回的全部字段，描述、评论、附件都在里面。

## 决策

1. **连通是两个工作区之间的关系，不是成员关系。** 表 `workspace_link` 记录「源方 → 看方 + 勾选的项目」。看方的人身份不变，在源方没有任何成员行，源方的既有接口一个都进不去（中间件按成员身份就直接 404）。
2. **非成员只读连通只有一个出口。** 看方读取源方数据只能经 `internal/workspacelink` 出去：`GET /api/workspace-links/{id}/view`，以及聊天、项目和自动化挂只读参考项目用的 `GET /api/workspace-links/projects` 和每次 run 认领时的重读。它们返回白名单 DTO：项目的标题、图标、状态、完成数和**项目上下文**（描述、资源的仓库地址和本地目录路径、项目记忆那一行），任务的编号、标题、状态、优先级、负责人名字、截止日和更新时间。任务描述、评论、附件、自定义属性、任务 ID、资源的机器信息（daemon、执行模式）都不在里面。DTO 字段有快照测试钉住，加字段就得改测试。
   DENE-897 另有基于成员身份的读取出口：`GET /api/links/issue`、`/api/links/issue/comments`、`/api/links/issue/timeline`，通过 `url` 指定任务。跨区调用只接受直接人类发起的 run，按发起人在目标工作区的成员身份、模块权限与资源可见性校验，不借连通授权；源方任务动态记 `cross_workspace_read`。返回带来源标记的任务、评论、动态和运行元数据，排除附件 URL、运行正文和日志。这不扩展非成员只读 DTO。
3. **判定集中在 `internal/workspacelink`。** `Decide(op, side, actor)` 一张表决定谁能做什么，测试把每一格都写死了。读取时再按源方的规则过滤：只看勾选的项目，项目和任务都必须不是 private；按「工作区可见」读取，不借任何人的身份。
4. **所有拒绝都是同一个 404 “link not found”。** 不存在、未接受、已断开、不是你这边、你是访客、项目被取消勾选，回的都是同一句话，不告诉对方哪一种。
5. **从看方这边拉（DENE-1582）。** 一个人同时是源方所有者、又是看方所有者或管理员时，可以在看方的设置里直接选源方的项目：一条连通要的两个决定（源方所有者发起、看方接受）他都有权做，`Pull` 在同一个事务里各记一条审计，连通立即生效。不满足就拒绝并说明要请源方所有者发起，不新增「申请」状态。
6. **共享项目就是共享项目上下文（DENE-1643）。** 不另设开关：源方勾选一个项目，看方就能读它的描述、资源和项目记忆，建连通的页面要把这句话写给源方看。看方的聊天、项目和自动化可以把它挂成「只读参考项目」，它只进简报里的参考段，永远不是 run 的工作项目：不决定代码来源，不在源方本地目录开 worktree 或提交，仓库只能 checkout 来读、不能推。本机没有那个目录时，简报用一句话说明，不报错。每次 run 认领都按发起人的身份重读一次连通，断开或取消勾选后下一次 run 就不再注入，设置和聊天里显示为失效。项目保存默认参考项目；自动化未设置（`null`）时继承所属项目，显式空列表（`[]`）表示不引用，非空列表完全替换项目默认值。项目下的任务、自动化的 `run_only` 以及 `create_issue` 产生的任务在认领时读取当时的设置。自动化任务沿用既有 `originator_user_id`：手动运行取发起人（智能体代办取它的 run 发起人），定时 / webhook 运行取触发器 `created_by` 对应的发起人；不重新借用自动化发布人、项目所有者或运行机器所有者。发起人缺失、离开看方工作区或降为访客时不注入源方上下文。设置只存 `link_id + project_id` 和用于显示失效项的名称快照，源方内容仍每次经 `internal/workspacelink` 重读；白名单 DTO 不加字段。
7. **智能体不管连通本身。** 带任务令牌的调用只能 `list` 和 `view` 自己所在工作区的连通，发起、改项目、接受、断开、开关托管一律 403。
8. **可托管是独立的写入出口，只开给看方的智能体（DENE-1663）。** 源方所有者可以把一条连通设为「可托管」（同时拥有两边的人也可以从看方开关，两边各记一条审计）。Kun 于 2026-10-11 决定：新建连通默认打开，可在创建时传 `managed:false` 关闭；默认允许按发起人已有权限代办，不新增其在源方的权限。只在创建事务应用默认值，不修改数据库列默认值、不回写现有连通。打开后，看方智能体的 run 在请求上带 `X-Linked-Workspace: <源方>`，就能以**这次 run 的发起人**的身份操作源方的任务和自动化，执行仍在源方。这是对「任务令牌只能用在绑定工作区」（MUL-2600）的写入例外（只读成员出口见第 2 条），由 `internal/workspacelink` 的 `Managed` 中间件在认证之后、所有工作区门之前判定，每次调用都重查：
   - 源方 → 看方的连通是 active 且托管开着；
   - 令牌对应的 run 还在跑，发起人是源方成员，`Decide(OpManageRemote)` 允许他的档位（成员及以上，访客不行）；
   - 路由在白名单里：任务的列表、搜索、批量/单项子任务、读取、新建、修改、评论列表/新增、时间线、标签列表/增删、属性设置/清空；自动化的列表、读取、新建、修改、暂停/恢复、立即运行、删除、运行列表/详情、触发器增改删、cron 预览、代办记录；附件上传 `POST /api/upload-file`；以及解析名字要用的只读查询（标签、属性、状态、项目、小队、智能体、成员列表及 `GET /api/projects/{id}/resources`）。聊天目录（`GET /api/chat/directory`）、本人聊天读取（`GET /api/chat/sessions/{id}` 和 `/messages`）与发送文本（`POST /api/chat/sessions/{id}/messages`）。聊天必须由本次 run 发起人本人创建，列表也只返回他的聊天，共享聊天不算；发送照常重新核对源方聊天智能体的调用权限并排队叫醒。成员管理、工作区设置、MCP、智能体配置、连通管理和其余接口都不开。
   路径参数只匹配规范 UUID；任务另外接受编号（如 `DENE-1812`）。固定路径不会被资源详情规则吞掉，`limit-usage`、`child-progress`、`parking`、`grouped`、`stall-actions`、`autopilots/usage` 均不放行。完整的方法、路径、审计标记与名称见 `server/internal/workspacelink/testdata/managed-routes.txt`，测试逐字核对，新增路由必须同步修改快照。
   `--linked` 附件沿用上传与评论绑定接口，上传者为 run 发起人，附件记录与存储路径归源方；上传时检查他在源方的权限，不能绑定看方任务。项目资源查询仍走源方项目访问检查。
   @ 或指派源方智能体允许沿源方普通触发流程起 run，发起人继承本次代办的人，仍受源方调用权限、路由与运行条件限制；任务写入留下代办动态，不把看方 runtime 所有者冒充发起人。
   通过后请求改写成发起人在源方的普通请求，后面的访客门和各接口自己的权限照常按他在源方的档位判。范围是整个源方工作区，不限于勾选的项目。关掉托管或断开连通，下一次调用就被拒。拒绝统一是 403，不说明是哪一条没过；提示用 `multica workspace link view` 核对连通。
   每次写入成功后留痕：`workspace_link_audit` 记一条 `managed_write`（发起人、看方工作区、智能体、路由）；任务上另记一条 `linked_write` 动态，显示为「<发起人> 经 <看方>·<智能体> 代办」；自动化上另记一条 `autopilot_linked_change`（新建时取响应里的 id），用 `GET /api/autopilots/{id}/linked-changes` 或 `multica autopilot linked-changes` 查。

### 聊天代发（DENE-1808）

聊天是可托管白名单的扩展，不增加接收聊天设置或第三个出口。`multica chat list|send --linked <源方>` 复用现有目录和消息接口；仅本人聊天、文本和排队模式，不开放附件、创建聊天、改标题、交棒、停止或重启。发起人在源方的身份始终来自已认证 run，不使用运行时所有者。

消息标注“<发起人> 经 <看方>·<智能体> 代发”，类型为 `linked_delivery`，不将正文算作人的原话。简报、历史、交接与回顾将正文 JSON 编码并包为外部粘贴内容，不解释其中提及为授权或指令。每条成功发送沿既有 `managed_write` 审计，额外记录目标 `chat_id`；源方聊天实时与历史都展示代发来源，原生 App 同步显示。开启可托管表示准许以现有权限代发，不表示信任外部正文中的要求。

## 理由

- 访客方案的漏洞面是「源方所有接口 × 每个字段」，单一出口的漏洞面只有一个接口和一份白名单。
- 连通不改四档档位矩阵的任何一格，权限底座不需要为它加例外。
- 断开后下一次读取就失效，不依赖缓存失效或会话过期。

## 后果

- 看方能看到的东西只有白名单这么多。项目上下文（DENE-1643）是加进白名单的第一批字段：源方写在项目描述和记忆里的内容会被看方的智能体读到。要再加字段（例如任务详情、评论），得改 DTO、快照测试和这份 ADR，不能顺手把既有接口开给看方。
- 一条连通只有一个看方；要给多个工作区看就建多条连通。连通增删、接受、项目名单和托管变更提交后向两边发送 `workspace_link:changed` 失效事件，不携带源方数据；客户端重读设置、阅读页和总览，重连补拉；看方写入只有可托管这一条路，而且只给智能体、只在白名单路由上。
- 可托管让看方智能体按发起人在源方的权限干活，等于把这个人在源方的写权限借给了看方的 run。所以开关只给源方所有者，范围宁窄勿宽：白名单之外的接口要开，得改 `managed.go` 的路由表、它的测试和这份 ADR。
- 审计记录写在 `workspace_link_audit`，双方所有者都能看。


## DENE-1811：设置同步与双向管理

看方的 owner/admin 同时是源方 owner 时，可从看方修改项目名单；`Decide(OpUpdateProjects)` 同时校验两边档位，事务内从源方校验非私密项目并在两边各记一条审计。智能体仍不能管理连通。两边名单均返回共享项目，看方始终排除已转私密的项目；待接受名单仅供人工管理者查看。

待接受连通不得开启托管；历史已开启值不迁移，仍可关闭，只有 active 连通实际授予托管权限。接口返回每条连通的 `can_update_projects` 和 `can_set_managed`，页面据此展示可用操作及原因。

审计按 `(created_at, id)` 降序游标分页，返回对方工作区、代办路由与对象标签；设置页与 `workspace link audit` 使用同一接口。原生手机 App 本票不变，由单独任务覆盖；共享 Web/Desktop 页面适配窄屏。
